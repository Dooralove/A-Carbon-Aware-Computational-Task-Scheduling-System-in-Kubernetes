# ADR-000: Базовые инженерные рамки проекта, границы Scope и режим SSOT

- **Статус:** accepted
- **Дата:** 2026-09-04
- **Авторы:** Lead Software Architect / Technical Governance Lead
- **Связанные документы:** [`docs/ssot/governance.md`](../ssot/governance.md), [`docs/ssot/engineering-specification.md`](../ssot/engineering-specification.md), [`docs/decisions_adr/README.md`](README.md)
- **Supersedes:** —
- **Superseded by:** —

## Контекст

Дипломный проект «Carbon-Aware Kubernetes Scheduler» разрабатывается мультиагентным пайплайном: разные агенты отвечают за исследование, архитектуру, реализацию на Go, инфраструктуру Kind, эксперименты и текст диплома. Задача T0.1 создала каркас репозитория (Standard Go Project Layout, `go.mod` с модулем `carbon-aware-k8s` и Go 1.23, `Makefile`, `.golangci.yml`, шаблон ADR, каталог `docs/ssot/` с преимущественно незаполненными документами). Исходного кода сервисов ещё нет.

Из этого вытекают три риска, каждый из которых способен сорвать работу сильнее, чем любая техническая ошибка.

**Риск 1 — scope creep.** Инженерная спецификация (§99, §131) уже прямо перечисляет то, что должно быть исключено: live migration, multi-cluster federation, carbon-aware HPA, ML-прогнозирование, PostgreSQL, Kafka, собственный scheduler с нуля, service mesh. Но перечисление разбросано по тексту объёмом свыше 3900 строк и сформулировано как рекомендация автора («я бы убрал»), а не как норма. Агент, читающий спецификацию частично, легко воспримет «Carbon-aware HPA — перспективное направление» как приглашение реализовать HPA.

**Риск 2 — расхождение агентов.** Без явного правила приоритета конфликт между агентами разрешается «последним записавшим»: каждый следующий агент правит документы под свою реализацию, и SSOT перестаёт быть источником истины. Каталог `docs/ssot/` уже содержит правило «расхождение SSOT и кода разрешается в пользу ADR + правки SSOT», но не определяет, кто вправе править SSOT и что делать агенту, обнаружившему противоречие.

**Риск 3 — невоспроизводимые эксперименты.** Главный результат работы — количественное сравнение стратегий планирования. Спецификация (§38, §93, §111) фиксирует, что live API непригоден для научного воспроизведения и что вывод по одному прогону недопустим, но не задаёт ни минимального N, ни состава фиксируемого окружения, ни формата идентификации прогона. Эксперимент, который нельзя повторить, на защите не стоит ничего.

Решение нельзя отложить: исследовательский этап (T1.1–T1.3) стартует немедленно, а любые артефакты, созданные до фиксации рамок, придётся переделывать.

Отдельно требует разрешения коллизия соглашений: `docs/decisions_adr/README.md` (T0.1) задаёт схему имён `NNNN-short-kebab-title.md`, тогда как принятая пайплайном схема нумерации — `NNN_snake_case_title.md`, начиная с `000`. Две конкурирующие схемы в одном каталоге — источник ровно того рода неоднозначности, который данный ADR призван устранить.

## Решение

Принимается документ [`docs/ssot/governance.md`](../ssot/governance.md) как нормативный акт проекта верхнего уровня. Он фиксирует пять групп норм.

**1. Границы проекта.** Восемнадцать обязательных артефактов (`SCOPE-IN-01..18`) и двадцать два строгих запрета (`SCOPE-OUT-01..22`). Запреты имеют предписывающий статус: любая работа, попадающая под запрет, не принимается целиком, без частичного зачёта. Снятие запрета возможно только новым ADR, утверждённым уровнем L0. Семь пограничных случаев (`SCOPE-EDGE-01..07`) закрывают известные неоднозначности; главный из них — `SCOPE-EDGE-01`: неоднозначность трактуется в пользу Out-of-Scope.

Явно и окончательно исключаются: live migration, cross-cluster federation, carbon-aware HPA, ML-прогнозирование нейросетями, внешние СУБД (PostgreSQL и аналоги), Kafka и брокеры сообщений, а также scheduler extender, собственный scheduler с нуля, service mesh, Redis, реальный multi-region, обязательная CRD, operator, rescheduling-контроллер, Python в production-контуре, обязательный Helm.

**2. Definition of Done.** Четыре независимых чеклиста: код (`DOD-CODE-01..13`), тесты (`DOD-TEST-01..10`), документация (`DOD-DOC-01..11`), эксперименты (`DOD-EXP-01..12`), плюс сводная таблица приёмки с указанием, кто её выполняет. Артефакт закрывается только при выполнении всех пунктов; заполненный чеклист прикладывается к отчёту агента.

**3. Code Style Guide.** Go (`GO-01..20`) — на базе Effective Go и Go Code Review Comments, с проектными усилениями: единицы измерения в именах идентификаторов, чистота вычислительных функций модели, запрет сетевых вызовов в горячем пути планировщика, запрет магических чисел в модели. Python (`PY-01..14`) — ограничен анализом результатов, требует пиннинга версий, seed, генерации всех чисел диплома скриптом и запрещает тяжёлый ML-стек. Конфигурационные форматы — `CFG-01..08`.

**4. Версионирование.** SemVer с мажором `0` до защиты и вехами `v0.1.0`/`v0.2.0`/`v0.3.0`/`v1.0.0`; Conventional Commits с обязательной ссылкой на задачу пайплайна; версионные шапки SSOT-документов; неизменяемость `accepted` ADR по смыслу; стабильность идентификаторов правил, требований и метрик (`VER-01..20`).

**5. Режим SSOT.** Вводятся четыре уровня доступа. **L0** — автор диплома и научный руководитель, полные права. **L1** — архитектор, единственный, кто пишет в `docs/ssot/` и выпускает ADR. **L2** — исполнительные агенты (исследование, Go, DevOps, эксперименты, текст), доступ к SSOT **только на чтение**. **L3** — вспомогательные агенты, только чтение.

Документы `docs/ssot/*.md` и `accepted` ADR объявляются **неизменяемыми для агентов уровня L2 и ниже** (`SSOT-01`). Прямое редактирование агентом L2/L3 признаётся нарушением процесса, и такое изменение откатывается независимо от содержательного качества правки. Вместо редактирования агент L2 оформляет SSOT Change Request по форме §5.3 governance и приостанавливает спорную часть работы до решения L1. При расхождении «код ↔ SSOT» прав SSOT (`SSOT-04`): сначала ADR и правка документа, затем код. Десять типов конфликтов между агентами получают детерминированное правило разрешения (`CONF-01..10`), включая жёсткий приоритет документов: `governance.md` → ADR → `requirements.md` → `architecture.md` → `interfaces.md` → `metrics.md` → `experiment-protocol.md` → `glossary.md`.

**6. Воспроизводимость.** Двадцать требований (`REPRO-01..20`): только replay mode для чисел, попадающих в диплом; версионированный датасет с sha256; явные seed; `run_id` фиксированного формата; обязательный `environment.yaml` с commit SHA, версиями инструментария, топологией и параметрами модели; N ≥ 5 повторов (N ≥ 10 для ключевых сценариев); публикация mean/median/p95 и разброса; критерий исключения прогона, заданный до прогонов; обязательный sensitivity analysis по некалиброванным параметрам энергомодели; полное отделение демонстрации на защите от экспериментальной части.

**Сопутствующее решение о соглашениях.** Каноническая схема имён ADR — `NNN_snake_case_title.md`, нумерация с `000`. `docs/decisions_adr/README.md` приводится в соответствие. Версия Python для аналитического контура фиксируется как 3.11 (в исходной спецификации не была задана). Версия Kubernetes остаётся на линии `1.37.x` согласно спецификации; точная patch-версия и digest node-образа kind фиксируются отдельным ADR инфраструктурного этапа до первого зачётного прогона.

## Обоснование

Выбранный подход исходит из того, что главный риск дипломной работы — не техническая сложность отдельного компонента, а неограниченный рост объёма и потеря согласованности между участниками. Спецификация уже содержит верные инженерные решения; недостающее звено — перевод их из жанра рекомендации в жанр нормы с идентификаторами, проверяемыми критериями и процедурой изменения.

Идентификаторы у каждого правила выбраны потому, что мультиагентный пайплайн нуждается в точных ссылках: отчёт агента «нарушает `SCOPE-OUT-03`» проверяем механически, а «выходит за рамки проекта» — нет. Стабильность идентификаторов (`VER-19`) позволяет ссылаться на нормы из кода, отчётов и текста диплома, не боясь смещения нумерации.

Режим «SSOT только для чтения ниже L1» выбран как единственный, дающий детерминированное разрешение конфликтов. Альтернатива — коллективное редактирование — на практике приводит к тому, что документ описывает последнюю реализацию, а не согласованное намерение, и теряет функцию источника истины. Издержка в виде процедуры Change Request сознательно принимается: она добавляет один шаг согласования, но делает каждое расширение Scope видимым.

Приоритет «SSOT прав, код правится» противоположен обычной инженерной практике «код — источник истины». Это осознанный выбор для исследовательской работы: защищается не программа, а алгоритм и его обоснование, поэтому расхождение реализации с зафиксированной моделью есть дефект реализации, а не устаревание документа.

Числовые пороги обоснованы так: покрытие 85 % для `pkg/energy`, `pkg/carbon` и scoring — потому что именно эти пакеты содержат защищаемую математическую модель, и ошибка в них обесценивает все эксперименты; 70 % для остальных пакетов — разумный уровень для исследовательского кода без избыточных затрат. N ≥ 5 — минимум, при котором осмысленны median и разброс; N ≥ 10 для ключевых сценариев — компромисс между статистической уверенностью и стоимостью прогона на локальном kind-стенде. Запрет live API в экспериментах прямо следует из §38 спецификации: одни и те же прогоны в разные дни дадут разные значения интенсивности и, следовательно, невоспроизводимый результат.

Запрет на Python в production-контуре и на тяжёлый ML-стек в аналитике — не стилистическое предпочтение, а способ удержать `SCOPE-OUT-04`: доступный `torch` в окружении рано или поздно превращается в «маленькую LSTM для прогноза интенсивности».

## Последствия

### Положительные

- Границы работы определены исчерпывающе и проверяемо; спор о принадлежности задачи Scope разрешается за одну проверку по списку.
- Каждый тип артефакта имеет формальный критерий приёмки, поэтому «сделано» перестаёт быть предметом переговоров.
- Конфликты между агентами разрешаются детерминированно, без эскалации к человеку в типовых случаях.
- Экспериментальные результаты защитимы: для любого числа в дипломе восстановимы окружение, датасет, seed и команда воспроизведения.
- Идентификаторы правил дают трассируемость «норма → код → отчёт → текст диплома».
- Внесение изменений в SSOT становится наблюдаемым событием с историей причин.

### Отрицательные / компромиссы

- Процедура Change Request замедляет исполнительных агентов: обнаружив пробел в SSOT, агент обязан остановиться и дождаться решения L1 вместо самостоятельной правки.
- Архитектор L1 становится узким местом: все правки SSOT и вся приёмка проходят через него.
- Требование N ≥ 5 (и N ≥ 10 для ключевых сценариев) кратно увеличивает машинное время экспериментального этапа.
- Порог покрытия 85 % на пакетах модели потребует заметных усилий на тестах, включая эталонные численные примеры, посчитанные вручную.
- Жёсткие запреты §1.3 закрывают несколько эффектно выглядящих направлений (HPA, миграция, ML-прогноз), что субъективно обедняет презентацию, хотя и повышает техническую корректность работы.
- Формализация вносит бюрократическую нагрузку, непропорциональную объёму кода на самых ранних задачах.

### Влияние на SSOT и код

- **Каталоги / пакеты:** зафиксирован Standard Go Project Layout; `cmd/` — только точки входа, логика в `pkg/`; запрещены пакеты `util`, `common`, `helpers`; запрещена зависимость `pkg/*` → `cmd/*`.
- **CRD / API:** CRD `CarbonPolicy` исключена из обязательного контура (`SCOPE-OUT-12`); конфигурация — ConfigMap плюс labels/annotations `carbon-aware.io/*`; группа API остаётся `carbon-aware.io/v1alpha1`.
- **Scheduler:** разрешены только extension points `PreScore`, `Score`, `NormalizeScore`; `QueueSort`, `Filter`, `Permit` запрещены (`SCOPE-OUT-16`); `Reserve` — по отдельному ADR; сетевые вызовы в горячем пути запрещены (`SCOPE-OUT-17`, `DOD-CODE-12`).
- **Эксперименты / метрики:** введены обязательные `run_id`, `environment.yaml`, карточка сценария; новая метрика Prometheus не существует, пока не описана в `metrics.md` (`DOD-CODE-13`).
- **Документы:** `docs/ssot/README.md` дополнен строкой про `governance.md` и уровнями доступа; `docs/decisions_adr/README.md` приведён к схеме имён `NNN_snake_case_title.md`, индекс ADR заполнен.
- **Инструментарий:** `.golangci.yml` и `Makefile` получают статус части SSOT-режима — ослабление набора линтеров или удаление цели сборки требует ADR.

## Альтернативы

| Вариант | Почему отклонён |
| --- | --- |
| Не вводить governance, опираться напрямую на `engineering-specification.md` | Спецификация написана в жанре рассуждения объёмом свыше 3900 строк, ограничения сформулированы как рекомендации автора и разбросаны по тексту. Агент, читающий её фрагментами, не получает проверяемых критериев приёмки |
| Мягкие рекомендации вместо запретов («избегать HPA») | Мультиагентный пайплайн трактует рекомендацию как разрешение при удобном случае. Опыт §99 спецификации показывает, что перечисленные направления притягательны именно своей эффектностью |
| Разрешить всем агентам править SSOT | Приводит к режиму «последний записавший прав»: документ начинает описывать последнюю реализацию, теряя функцию источника истины и способность разрешать конфликты |
| Код как источник истины, документация — производная | Для исследовательской работы защищается модель, а не программа. При таком приоритете любое отклонение реализации автоматически переписывало бы защищаемую модель |
| Отложить фиксацию Scope до конца исследовательского этапа (после T1.x) | Агенты T1.1–T1.3 без границ исследуют в том числе заведомо исключённые направления (federation, ML-прогноз), и их выводы придётся отбрасывать |
| Вынести DoD в отдельный документ | Разделение Scope и DoD снижает вероятность, что агент прочитает оба. Единый нормативный документ читается один раз в начале работы |
| Использовать live API в экспериментах ради реалистичности | Значения интенсивности меняются между прогонами, результаты неповторимы, сравнение стратегий теряет валидность. Live-режим сохранён исключительно для демонстрации на защите |
| Ограничиться N = 1..2 прогонами ради экономии времени | Не позволяет отличить эффект алгоритма от шума планирования; вывод «снижение на X %» по одному прогону не выдержит вопроса комиссии |
| Сохранить схему имён ADR `NNNN-short-kebab-title.md` из T0.1 | Конфликтует с принятой пайплайном нумерацией с `000` и требуемым именем данного ADR; две схемы в одном каталоге порождают ту самую неоднозначность, которую документ устраняет |

## Проверка

Соблюдение решения проверяется следующим образом.

1. **Scope.** Перед закрытием любой задачи агент проходит по списку `SCOPE-OUT-01..22` и фиксирует результат самопроверки в отчёте (`DOD-CODE-10`). Наличие в репозитории зависимости на СУБД, брокер сообщений, ML-фреймворк или контроллер миграции — немедленный признак нарушения, обнаруживаемый просмотром `go.mod`, `analysis/requirements.txt` и `deployments/`.
2. **DoD.** Отчёт агента в `docs/audit/` содержит заполненный чеклист применимого типа. Отсутствие чеклиста означает, что задача не закрыта (`CONF-09`).
3. **Стиль и качество кода.** Автоматически: `make lint` и `make test` с нулевым кодом возврата; покрытие — `go test -cover` с порогами из `DOD-CODE-04`; гонки — `go test -race`.
4. **Версионирование.** Ревью истории git: соответствие имён веток `VER-08`, сообщений — Conventional Commits (`VER-09`), наличие обновления SSOT в том же коммите, что и изменение поведения (`VER-11`).
5. **Режим SSOT.** Ревью diff: изменения в `docs/ssot/*` и `accepted` ADR, внесённые агентом уровня L2/L3, откатываются (`SSOT-01`). Каждая правка SSOT должна сопровождаться либо ADR, либо решением L1 по Change Request.
6. **Воспроизводимость.** Контрольная процедура: взять произвольный `run_id`, упомянутый в тексте диплома, восстановить окружение по `environment.yaml`, повторить прогон и сравнить агрегаты. Расхождение вне заявленного разброса означает нарушение `REPRO-01..17`. Дополнительно: прогон, выполненный на «грязном» рабочем дереве, недействителен согласно составу manifest окружения (governance, §6.3).
7. **Согласованность документов.** Периодическая сверка `governance.md` с остальными SSOT-файлами на противоречия; при обнаружении применяется приоритет `CONF-03`, противоречие устраняется правкой, а не фиксируется как известное.
