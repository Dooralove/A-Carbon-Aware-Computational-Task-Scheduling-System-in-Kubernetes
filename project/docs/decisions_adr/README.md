# Architecture Decision Records (ADR)

Каталог фиксирует **архитектурные решения**, которые нельзя восстановить только по коду: выбор планировщика, модели углерода, источника интенсивности, протокола экспериментов, контрактов API.

SSOT (`docs/ssot/`) описывает *текущее* состояние системы. ADR описывает *почему* оно такое и какие варианты отвергнуты. При конфликте сначала обновляют ADR, затем SSOT.

## Когда писать ADR

Пишите ADR, если решение:

- меняет границы компонентов (`cmd/`, `pkg/`, `api/`);
- выбирает внешнюю зависимость или источник данных (электрическая сеть, carbon intensity API, метрики узлов);
- фиксирует протокол эксперимента или KPI дипломной работы;
- отклоняет очевидную альтернативу (например, расширение kube-scheduler vs отдельный scheduler plugin).

Не пишите ADR для локального рефакторинга, переименования без смены контракта и чисто стилистических правок.

## Именование файлов

```
NNN_snake_case_title.md
```

- `NNN` — трёхзначный порядковый номер, нумерация с `000`. Номер не переиспользуется.
- `snake_case_title` — кратко, на английском, без даты в имени.
- Шаблон: [`template.md`](template.md). Копия шаблона **не** является ADR.

Пример: `001_scheduler_plugin_vs_extender.md`.

Схема закреплена ADR-000; изменение схемы требует нового ADR.

## Жизненный цикл статуса

| Статус | Смысл |
| --- | --- |
| `proposed` | обсуждается, ещё не обязательно для реализации |
| `accepted` | принято; реализация и SSOT должны соответствовать |
| `deprecated` | больше не рекомендуется, но исторически верно |
| `superseded` | заменено другим ADR (указать номер) |

Менять смысл уже `accepted` ADR нельзя: выпускайте новый ADR со статусом `accepted` и помечайте старый как `superseded`.

## Правила оформления

1. Один файл — одно решение.
2. Заполняйте все секции шаблона; пустые секции не оставляйте (напишите «не применимо»).
3. Ссылайтесь на SSOT по относительному пути, не дублируйте длинные спецификации.
4. Язык: русский (диплом), технические идентификаторы — как в коде (`carbon-service`, `pkg/energy`).
5. Дата — день принятия (или первого `proposed`), формат ISO-8601.

## Процесс

1. Скопировать `template.md` → `NNN_snake_case_title.md`.
2. Заполнить контекст, решение, последствия, альтернативы.
3. Поставить `proposed`, пройти ревью (человек или агент-архитектор).
4. После согласия: `accepted`, обновить затронутые файлы в `docs/ssot/`.
5. Упомянуть номер ADR в PR / отчёте агента.
