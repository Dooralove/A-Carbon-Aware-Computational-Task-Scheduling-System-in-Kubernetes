## Результат

Зафиксирована двухпроцессная архитектура с гарантированной асинхронностью углеродных данных:

1. CDS (адаптеры, Replay Engine, in-memory cache, REST) не ранжирует узлы.
2. Custom kube-scheduler содержит `CarbonAware` (PreScore \(O(NK)\), Score \(O(1)\), NormalizeScore) и Cache Sync Worker.
3. Плагин читает только локальный immutable snapshot; HTTP к CDS есть исключительно у Worker.
4. Изоляция A/B/C: kind `default-scheduler` vs custom `carbon-aware-scheduler` / `carbon-only-scheduler`.
5. Четыре PlantUML-диаграммы встроены в SSOT (§4, §9–§11).

## Проверка диаграмм

Официальный `plantuml.jar` в рабочее дерево не загружался (ограничение среды). Выполнена структурная проверка четырёх блоков `@startuml`/`@enduml`: баланс `alt`/`loop`/`par`/`note`/`{}`, объявление alias на стрелках, запрет незакавыченных запятых в `[component]`.

Инварианты потоков (PASS):

- нет ребра scheduler ↔ Electricity Maps;
- `KCS --> CDS` подписан Cache Sync Worker;
- Prometheus не пушит в runtime (только scrape);
- `CarbonAware plugin` не имеет стрелки на REST; есть `Cache Sync Worker --> REST`;
- sequence планирования не содержит REST/CDS; `Score` читает `CycleState` с пометкой No HTTP;
- sequence sync: REST вызывает только Worker; `PreScore` делает `Load()` снимка.

## Решения сверх входа спецификации (`CONF-05`)

| Решение | Почему |
| --- | --- |
| HTTP к CDS только из Worker, не из PreScore | PreScore на сериализованном scheduling cycle; таймаут CDS иначе задерживает все Pod |
| Baseline A = kind kube-scheduler | нет конфликта `schedulerName`/лидерства; A = штатный планировщик |
| Третий профиль `carbon-only-scheduler` | SCOPE-IN-13 + ловушка `multiPoint`+`disabled: '*'` (T1.3) |
| `pkg/provider` / `pkg/replay` вне `pkg/carbon` | чистые формулы (LOCKED) без I/O |
