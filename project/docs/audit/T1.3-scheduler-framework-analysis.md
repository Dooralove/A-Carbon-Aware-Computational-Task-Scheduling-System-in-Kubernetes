## Ключевые результаты

1. Зафиксирована актуальная раскладка типов: с 1.34 `CycleState`, `NodeInfo`, `Status`, `Code`
   переехали в staging `k8s.io/kube-scheduler/framework` и **стали интерфейсами**; с 1.35 туда же
   переехали интерфейсы точек расширения и `Handle`.
2. Составлена матрица изменения сигнатур 1.28 → 1.37 (`PreScore` — 1.30, `Score` — 1.33).
3. Разобрана модель конкурентности: `Score` вызывается параллельно (до 16 goroutine) по узлам
   одного Pod с общим `CycleState`; `PreScore` — один раз на Pod; цикл привязки — отдельная
   goroutine, разделяющая тот же `CycleState`.
4. Обоснован набор `PreScore` + `Score` + `NormalizeScore` и отказ от `QueueSort` (в том числе
   технический аргумент: `validateCommonQueueSort` требует одинаковый `queueSort` во всех профилях,
   что уничтожило бы baseline A).
5. Описан контракт нормализации: проверка \([0,100]\) выполняется **после** `NormalizeScore`,
   нарушение даёт статус `Error` и прерывает цикл планирования.
6. Посчитан суммарный вес стандартных Score-плагинов в 1.37 — **13**; отсюда требование задавать вес
   `CarbonAware` явно.
7. Предложена схема передачи данных `PreScore` → `Score` через один неизменяемый объект в
   `CycleState` и схема фонового обновления кэша через `atomic.Pointer`, удовлетворяющая
   `SCOPE-OUT-17` и `DOD-CODE-12`.
8. Обнаружена ловушка конфигурации профиля стратегии B: `score.disabled: ['*']` обрывает развёртку
   `multiPoint` целиком (`expandMultiPointPlugins`, проверка `disabledSet.Has("*")` стоит до
   развёртки), то есть отключает и `CarbonAware`. Планировщик стартует без ошибки, профиль остаётся
   без оценки узлов. Рабочий вариант — явная регистрация в `preScore.enabled`/`score.enabled`.

## SSOT Change Request

### CR-1. Синхронизация Go с Kubernetes 1.37

- **Затронутый документ и раздел:** [`docs/ssot/governance.md`](../ssot/governance.md) §3.1 («Go 1.23
  (см. `go.mod`)»); [`go.mod`](../../go.mod), директива `go 1.23`; `engineering-specification.md`
  §51 и §«Итоговая архитектура» («Kubernetes 1.37.x»).
- **Наблюдаемое противоречие:** Kubernetes v1.37.0 собран Go 1.26.5; директива `go` во всех модулях
  `k8s.io/*` версии 1.37 — `1.26.0` (проверено по `staging/src/k8s.io/apiserver/go.mod` и
  CHANGELOG-1.37: «Kubernetes is now built with Go 1.26.5»). Модуль с директивой `go 1.23` не
  собирается с зависимостью, требующей `go 1.26`.
- **Почему нужна правка:** `SCOPE-IN-01` предусматривает сборку плагина в бинарь `kube-scheduler`,
  поэтому toolchain проекта должен удовлетворять минимальной версии Go его зависимостей. Для
  Kubernetes 1.37 рабочая конфигурация известна: Go 1.26.x. Это синхронизация инструментальных
  версий, а не ограничение Scheduler Framework.
- **Предлагаемая формулировка:** в `governance.md` §3.1 заменить «Go 1.23 (см. `go.mod`)» на
  «Go 1.26 (см. `go.mod`); версия следует минимальной версии Go, требуемой зафиксированной
  patch-версией Kubernetes, и изменяется вместе с ней»; в `go.mod` — `go 1.26.0`.
- **Влияние на Scope:** в §1.3 не попадает; это уточнение инструментальной версии, не расширение
  предмета.
- **Альтернатива без изменения SSOT:** понизить целевую версию Kubernetes до той, что совместима с
  Go 1.23 (1.31–1.32). Оценка: хуже. Потребует правки `engineering-specification.md` (входной канон,
  `CONF-05`), даст устаревший API (`Score` с `nodeName`, `CycleState` как структура) и ослабит
  тезис об актуальности работы. Рекомендуется CR-1.

### Разрешение вопроса SLA на Quality Gate 1

`SCOPE-IN-06` задаёт expected runtime таблицей «класс workload → expected runtime». Поэтому в
принятой модели предикат
\(t_{\mathrm{now}}+\widehat T_{\mathrm{class}(p)}\le t_{\mathrm{deadline},p}\) является
workload-level условием, одинаковым для всех узлов. `CarbonAware.PreScore` проверяет его до
углеродных расчётов и при нарушении возвращает `fwk.Error` с причиной `SLA precondition failed`.
Runtime Scheduler Framework завершает попытку до `Score`; Pod остаётся `Pending` и следует
стандартному backoff/retry. Это fail-closed проверка конфигурации workload, а не temporal shifting:
для допуска требуется исправление deadline или класса runtime. Поведение и отдельная метрика
`sla_rejection_total` закрепляются integration-тестом на целевой patch-версии Kubernetes 1.37.
Ресурсно допустимое множество до этого формируют стандартные `Filter`-плагины, включая
`NodeResourcesFit`.

Таким образом, SLA и ресурсная выполнимость применяются до carbon scoring штатными механизмами
Scheduler Framework при сохранении разрешённого набора `PreScore` + `Score` + `NormalizeScore`.
Вопрос закрыт без изменения Scope и без добавления собственного `Filter`. Открытым остаётся CR-1 —
синхронизация версии toolchain перед сборкой; математическому этапу она не препятствует.

## Открытые вопросы (передаются дальше)

1. **Patch-версия Kubernetes** и digest node-образа kind — остаётся открытым с T0.2 и определяет
   точную patch-версию Go 1.26.x (CR-1).
2. **Значение веса `CarbonAware`** в `KubeSchedulerConfiguration` — параметр эксперимента, а не
   деталь конфигурации; должен попадать в `environment.yaml` прогона (`REPRO-06`, `REPRO-08`).
3. **Эффект «стада»** при пачечной подаче нагрузки: нужен ли `Reserve` (требует ADR по
   `SCOPE-OUT-16`) или достаточно ресурсной составляющей \(S_R\). Предлагается отдельный
   экспериментальный сценарий «поштучная против пачечной подачи».
4. **Разрешающая способность шкалы**: гипотеза о необходимости внутреннего fixed-point масштаба
   \([0,10000]\) требует проверки на реальном датасете CI и топологии стенда.
5. **Метрика разброса взвешенных оценок по плагинам** — кандидат в [`metrics.md`](../ssot/metrics.md)
   (`DOD-CODE-13`); без неё невозможно отличить «алгоритм не даёт эффекта» от «эффект перебит
   стандартными плагинами».
