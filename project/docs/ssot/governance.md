# Governance: границы проекта, качество и регламент SSOT

- **Версия:** 1.4.0
- **Статус:** accepted
- **Дата:** 2026-09-04
- **Владелец:** Lead Software Architect / Technical Governance Lead
- **Основание:** [engineering-specification.md](engineering-specification.md), ADR [`000_project_scope_and_governance.md`](../decisions_adr/000_project_scope_and_governance.md), Freeze [`002_system_architecture_and_api_freeze.md`](../decisions_adr/002_system_architecture_and_api_freeze.md)
- **Уровень изменяемости:** L1 (см. §5.1). Агенты уровня L2 и ниже изменять документ не вправе.

Документ является нормативным. Все остальные артефакты репозитория (код, манифесты, эксперименты, текст диплома, отчёты агентов) обязаны ему соответствовать. Формулировки «должен», «обязан», «запрещено» имеют предписывающий смысл; «рекомендуется» — необязательный.

Каждое правило имеет стабильный идентификатор (`SCOPE-IN-01`, `DOD-CODE-03`, …). Идентификаторы не переиспользуются и не перенумеровываются: отменённое правило помечается `[отменено ADR-NNN]`, но остаётся в документе.

## 1. Scope & Out-of-Scope

### 1.1. Предмет работы (одно предложение)

Разработка и экспериментальное исследование Kubernetes Scheduler Plugin, выбирающего узел для гибких (batch/flexible) вычислительных нагрузок по ожидаемому углеродному следу выполнения при соблюдении ресурсных ограничений и SLA.

### 1.2. In-Scope: обязательные артефакты

Артефакт считается обязательным, если без него дипломная работа не может быть защищена. Все пункты ниже обязательны.

| ID | Артефакт | Минимально достаточное состояние |
| --- | --- | --- |
| SCOPE-IN-01 | Scheduler Plugin `CarbonAware` на Go, собранный в бинарь kube-scheduler | Реализованы `PreScore`, `Score`, `NormalizeScore`; регистрируется через `KubeSchedulerConfiguration` как отдельный профиль `carbon-aware-scheduler` |
| SCOPE-IN-02 | Carbon Data Service (Go, отдельный процесс/образ) | HTTP REST: `/api/v1/zones`, `/api/v1/zones/{zone}/current`, `/api/v1/zones/{zone}/forecast`, `/api/v1/health`; кэш, валидация, freshness |
| SCOPE-IN-03 | Провайдеры данных углеродной интенсивности | Минимум три: `MockProvider`, `HistoricalDatasetProvider` (replay), `ElectricityMapsProvider` (live, только для демонстрации) |
| SCOPE-IN-04 | Модель энергопотребления узла | \(P(u)=P_{idle}+(P_{max}-P_{idle})\,u\) с задокументированной калибровкой и sensitivity analysis |
| SCOPE-IN-05 | Модель углеродного следа | Дискретная сумма \(CF=\sum_i P_i\,\Delta t_i\,CI_i\), а не произведение на текущую интенсивность |
| SCOPE-IN-06 | Модель оценки времени выполнения | Таблица `workload class → expected runtime`, полученная измерением на стенде |
| SCOPE-IN-07 | Многокритериальная функция оценки | \(S=w_C S_C+w_R S_R+w_P S_P\), \(\sum w_i=1\), нормализация в `[0,100]` |
| SCOPE-IN-08 | Hard constraints | Ресурсная выполнимость и SLA — жёсткие ограничения, применяются до carbon scoring |
| SCOPE-IN-09 | Fallback-поведение | Цепочка `fresh cache → stale cache → отключение carbon scoring → baseline behaviour`; отказ источника не ломает планирование |
| SCOPE-IN-10 | Конфигурация политики | ConfigMap + labels/annotations на Pod (`carbon-aware.io/*`). CRD — не обязательна (см. SCOPE-OUT-12) |
| SCOPE-IN-11 | Экспериментальный кластер | kind, ≥1 control-plane и ≥4 worker, логические энергозоны через label `carbon-aware.io/zone` |
| SCOPE-IN-12 | Мониторинг | Prometheus + Grafana dashboard; метрики плагина и сервиса |
| SCOPE-IN-13 | Три стратегии сравнения | A — `default-scheduler`; B — carbon-only (min CI); C — предлагаемый многокритериальный алгоритм |
| SCOPE-IN-14 | Экспериментальная программа | Сценарии: baseline, carbon-aware, sweep по весам, SLA, волатильность CI, отказ источника, overhead планировщика, масштабирование по числу узлов |
| SCOPE-IN-15 | Анализ на Python | Обработка результатов, статистика, графики (в т.ч. Pareto frontier «carbon vs runtime») |
| SCOPE-IN-16 | Тесты | unit, integration, e2e, failure-scenarios (см. §2.2) |
| SCOPE-IN-17 | Документация SSOT + ADR | Актуальные `docs/ssot/*`, ADR на каждое архитектурное решение |
| SCOPE-IN-18 | Текст диплома | `docs/diploma_text/`, трассируемый к SSOT и результатам экспериментов |

### 1.3. Out-of-Scope: строго запрещено

Пункты ниже **запрещены к реализации** в рамках диплома. Запрет действует на код, манифесты, зависимости, эксперименты и на формулировки в тексте диплома. Снятие запрета возможно **только** новым ADR со статусом `accepted`, утверждённым уровнем L0/L1; никакой агент не вправе трактовать запрет как «мягкую рекомендацию».

| ID | Запрещено | Почему | Допустимая замена |
| --- | --- | --- | --- |
| SCOPE-OUT-01 | **Live migration** запущенных Pod / контейнеров | Kubernetes не выполняет живую миграцию Pod между узлами; это не задача scheduler | Решение принимается только при первичном размещении Pod |
| SCOPE-OUT-02 | **Cross-cluster / multi-cluster federation**, KubeFed, глобальный мета-scheduler | Один kube-scheduler работает в пределах одного кластера | Логические энергозоны через label `carbon-aware.io/zone` внутри одного кластера |
| SCOPE-OUT-03 | **Carbon-aware HPA** и любое изменение числа реплик по углеродному сигналу | Смешивает семантику «сколько реплик» и «куда разместить», требует другой SLA-модели | Упомянуть как «перспективное направление дальнейшей работы» в тексте диплома |
| SCOPE-OUT-04 | **ML-прогнозирование нейросетями** (LSTM/Transformer/любые обучаемые модели прогноза CI) | Уводит работу в ML и делает результат непрозрачным | Внешний forecast источника, historical replay, persistence-модель \(\widehat{CI}(t+\Delta)=CI(t)\) |
| SCOPE-OUT-05 | **PostgreSQL и любые внешние СУБД** (MySQL, MongoDB, TimescaleDB, ClickHouse …) | Не требуется для задач диплома, раздувает инфраструктуру | Prometheus для временных рядов; CSV/Parquet для датасетов; SQLite — только при явном ADR |
| SCOPE-OUT-06 | **Kafka и любые брокеры сообщений** (RabbitMQ, NATS, Pulsar) | Нет асинхронного контура, требующего брокера | Прямые вызовы HTTP + in-memory cache |
| SCOPE-OUT-07 | **Собственный kube-scheduler с нуля** | Scheduler Framework уже даёт точки расширения | Plugin, скомпилированный в kube-scheduler |
| SCOPE-OUT-08 | **Scheduler Extender** (HTTP webhook вместо plugin) | Медленно и архитектурно слабее, чем in-tree plugin | Scheduler Framework plugin |
| SCOPE-OUT-09 | **Service mesh** (Istio, Linkerd) | Не влияет на предмет исследования | Обычные Service + NetworkPolicy |
| SCOPE-OUT-10 | **Redis / Memcached** как отдельный компонент | Кэш нужен только внутрипроцессный | In-memory cache в Carbon Data Service |
| SCOPE-OUT-11 | **Реальный multi-region / multi-cloud** (AWS, GCP, Azure billing, cloud API) | Не воспроизводимо, не нужно для доказательства алгоритма | Локальный kind + логические энергозоны |
| SCOPE-OUT-12 | **CRD `CarbonPolicy` как обязательный механизм** | Усложняет MVP, не даёт научного вклада | ConfigMap + labels/annotations; CRD допустима только после полностью работающей системы и только отдельным ADR |
| SCOPE-OUT-13 | **Kubernetes Operator / controller-runtime** для основной функциональности | Вне предмета: предмет — алгоритм выбора узла | Stateless plugin |
| SCOPE-OUT-14 | **Rescheduling / eviction controller**, descheduler, anti-thrashing логика | Расширение, не MVP | Раздел «дальнейшая работа» |
| SCOPE-OUT-15 | **Аппаратные измерители мощности как обязательное требование** (RAPL, IPMI, внешний ваттметр как единственный источник) | В виртуализованной среде недостоверно | Калиброванная модель + явное указание допущения |
| SCOPE-OUT-16 | **Использование `QueueSort`, `Filter`, `Permit` extension points** | Ломает базовые гарантии планировщика; предупреждение в hardening guide Kubernetes | Только `PreScore` / `Score` / `NormalizeScore`; `Reserve` — по отдельному ADR |
| SCOPE-OUT-17 | **HTTP-запросы к внешнему API или Prometheus внутри `Score()`** | Непредсказуемая задержка цикла планирования | Предзагруженный кэш/состояние, обновляемое вне цикла планирования |
| SCOPE-OUT-18 | **Сетевой, storage и embodied carbon** в модели | Невозможно достоверно оценить на стенде | Явно указать как ограничение работы |
| SCOPE-OUT-19 | **Production-развёртывание, multi-tenancy, HA, autoscaling самого сервиса** | Работа исследовательская | Один экземпляр сервиса на стенде |
| SCOPE-OUT-20 | **Части production-логики на Python** | Scheduler Framework — Go | Python только для анализа и генерации графиков (§3.2) |
| SCOPE-OUT-21 | **Helm как обязательное требование** | Не добавляет научной ценности | Голые манифесты в `deployments/kubernetes/`; Helm — опционально, при остатке времени |
| SCOPE-OUT-22 | **Заявления о новизне вида «впервые в мире»** и обещание конкретного процента снижения CO₂ до эксперимента | Недоказуемо | Формулировки из §12 «Ожидаемый результат» инженерной спецификации |

### 1.4. Пограничные случаи (разрешение неоднозначностей)

| ID | Ситуация | Однозначное решение |
| --- | --- | --- |
| SCOPE-EDGE-01 | Агент считает, что задача «почти» относится к Out-of-Scope | Считается Out-of-Scope. Бремя доказательства — на том, кто хочет включить |
| SCOPE-EDGE-02 | Узел без label `carbon-aware.io/zone` | Узел **не исключается**; получает нейтральный carbon score |
| SCOPE-EDGE-03 | Нет прогноза CI | Используется persistence-модель; факт помечается в метрике качества данных и в отчёте прогона |
| SCOPE-EDGE-04 | Данные старше `maxDataAgeSeconds` (по умолчанию 300 с) | Carbon scoring отключается, плагин возвращает нейтральный score, инкрементируется `fallback_total` |
| SCOPE-EDGE-05 | Нужна новая внешняя зависимость (Go module / Python package) | Требуется запись в ADR при добавлении runtime-зависимости; dev/test-зависимости — без ADR |
| SCOPE-EDGE-06 | Live API Electricity Maps | Разрешён **только** для демонстрации на защите. В экспериментах, результаты которых попадают в диплом, запрещён (§6) |
| SCOPE-EDGE-07 | Cost как критерий \(S_K\) | Включается только в эксперимент с различающимися energy-профилями узлов; иначе \(w_K=0\) и слагаемое не используется |

## 2. Definition of Done (DoD)

Артефакт считается «сделанным» только при выполнении **всех** пунктов соответствующего чеклиста. Частичное выполнение = задача не закрыта. Агент, закрывающий задачу, обязан приложить в отчёте заполненный чеклист с отметками.

### 2.1. DoD: код

| ID | Критерий |
| --- | --- |
| DOD-CODE-01 | Код компилируется: `make build` завершается с кодом 0 |
| DOD-CODE-02 | `make lint` (golangci-lint по `.golangci.yml`) — 0 замечаний. Подавления `//nolint` допустимы только с указанием линтера и причины: `//nolint:errcheck // причина` |
| DOD-CODE-03 | `make test` — все тесты зелёные, без `t.Skip` без объяснения |
| DOD-CODE-04 | Покрытие: пакеты `pkg/energy`, `pkg/carbon`, `pkg/scheduler` (scoring/normalization) — ≥ 85 % строк; остальные пакеты `pkg/` — ≥ 70 %; `cmd/` не нормируется |
| DOD-CODE-05 | Публичные типы, функции и методы имеют godoc-комментарий, начинающийся с имени идентификатора |
| DOD-CODE-06 | Нет TODO/FIXME без ссылки на задачу или ADR |
| DOD-CODE-07 | Нет секретов, API-ключей, токенов, персональных путей в коде и манифестах. Ключи — только через Secret / переменные окружения |
| DOD-CODE-08 | Изменение поведения отражено в соответствующем файле `docs/ssot/` в том же коммите/PR |
| DOD-CODE-09 | Новая внешняя runtime-зависимость сопровождается ADR (SCOPE-EDGE-05) |
| DOD-CODE-10 | Изменение не нарушает ни один пункт §1.3 (самопроверка по списку `SCOPE-OUT-*`) |
| DOD-CODE-11 | Ошибки обрабатываются и оборачиваются (`fmt.Errorf("...: %w", err)`); паника в библиотечном коде запрещена |
| DOD-CODE-12 | Код плагина в горячем пути (`PreScore`/`Score`) не выполняет сетевых вызовов, обращений к диску и блокирующих ожиданий |
| DOD-CODE-13 | Новые метрики Prometheus зарегистрированы в [metrics.md](metrics.md) с именем, типом, лейблами и единицами измерения |

### 2.2. DoD: тесты

| ID | Критерий |
| --- | --- |
| DOD-TEST-01 | Тесты детерминированы: без `time.Now()` в проверяемой логике (время инжектируется), без сетевых вызовов, без зависимости от порядка map |
| DOD-TEST-02 | Табличные тесты для чистых функций (модели энергии, углерода, нормализации, scoring) |
| DOD-TEST-03 | Каждая формула из математической модели покрыта тестом с эталонным численным примером, вычисленным вручную и указанным в комментарии |
| DOD-TEST-04 | Граничные случаи покрыты явно: `CI < 0`, `NaN`, timestamp в будущем, неизвестная зона, пустое множество допустимых узлов, `CF_max == CF_min` (деление на ноль при нормализации), нулевой runtime |
| DOD-TEST-05 | Integration-тесты проверяют связку Carbon Data Service ↔ Plugin на фиктивных данных, без внешней сети |
| DOD-TEST-06 | E2E-тест: создание Pod с `schedulerName: carbon-aware-scheduler` → проверка, что выбран ожидаемый узел при заданном датасете CI |
| DOD-TEST-07 | Failure-сценарии покрыты тестом: источник недоступен, данные stale, данные невалидны, Prometheus недоступен. Ожидание — деградация, а не отказ планирования |
| DOD-TEST-08 | Тесты разложены по `tests/unit`, `tests/integration`, `tests/e2e` либо рядом с пакетом (`*_test.go`) — выбранное соглашение единообразно по репозиторию |
| DOD-TEST-09 | Время прогона unit-тестов всего модуля — не более 60 с на типовой машине; медленные тесты помечаются `testing.Short()` |
| DOD-TEST-10 | Падающий тест не «чинится» ослаблением проверки без записи причины в отчёт агента |

### 2.4. DoD: эксперименты

| ID | Критерий |
| --- | --- |
| DOD-EXP-01 | Существует карточка эксперимента в `experiments/scenarios/<scenario-id>.yaml|md` с гипотезой, независимыми и зависимыми переменными, фиксированными параметрами |
| DOD-EXP-02 | Прогон выполнен в **replay mode** на зафиксированном датасете; live API запрещён (SCOPE-EDGE-06) |
| DOD-EXP-03 | Прогон повторён не менее **5 раз** (N ≥ 5) с одинаковой конфигурацией; единичный прогон не является результатом |
| DOD-EXP-04 | Зафиксирован `run_id` и manifest окружения (§6.3) |
| DOD-EXP-05 | Сравнение всегда включает baseline A (`default-scheduler`); для итоговых выводов — также baseline B (carbon-only) |
| DOD-EXP-06 | Результаты приведены как mean, median, p95 и разброс (std либо доверительный интервал); одно число без разброса не публикуется |
| DOD-EXP-07 | Сырые результаты сохранены в машиночитаемом виде (CSV/Parquet/JSON) в `experiments/results/<run_id>/`; крупные файлы — вне git с указанием sha256 и способа получения |
| DOD-EXP-08 | Скрипт анализа в `analysis/` воспроизводит все графики и числа из сырых данных одной командой |
| DOD-EXP-09 | Каждый вывод сопровождается указанием ограничений (какие допущения модели влияют на результат) |
| DOD-EXP-10 | Аномальный или отрицательный результат публикуется наравне с положительным; отбрасывание прогонов запрещено без записанного в карточке критерия исключения, заданного **до** прогона |
| DOD-EXP-11 | Для энергетической модели проведён sensitivity analysis по \(P_{idle}\), \(P_{max}\) |
| DOD-EXP-12 | Ручные правки кластера вне сценария запрещены; всё, что делает прогон, лежит в репозитории |

### 2.5. DoD: сводная таблица приёмки

| Тип артефакта | Приёмку выполняет | Формальный критерий приёмки |
| --- | --- | --- |
| Код (Go) | Архитектор (L1) | `DOD-CODE-01..13` = все ✅ |
| Тесты | Архитектор (L1) | `DOD-TEST-01..10` = все ✅ |
| SSOT-документ | Архитектор (L1) | `DOD-DOC-01..09` = все ✅ + отсутствие противоречий с §1 |
| ADR | Архитектор (L1) + L0 при снятии запрета из §1.3 | Все секции шаблона заполнены, индекс обновлён |
| Эксперимент | Исследователь (L2) + архитектор (L1) | `DOD-EXP-01..12` = все ✅ |
| Глава диплома | L0 (автор/руководитель) | `DOD-DOC-10` + трассировка к SSOT и `run_id` |

## 5. Регламент SSOT и разрешение конфликтов между агентами

### 5.1. Уровни доступа агентов

| Уровень | Кто | Права относительно SSOT |
| --- | --- | --- |
| **L0** | Автор диплома, научный руководитель | Полные. Может отменить любое решение, включая §1.3 |
| **L1** | Lead Software Architect / Technical Governance Lead | Пишет и изменяет `docs/ssot/*`, выпускает и принимает ADR, выполняет приёмку артефактов |
| **L2** | Исполнительные агенты: исследователь (T1.x), backend/Go, DevOps, аналитик экспериментов, технический писатель | **Только чтение** SSOT. Изменение — исключительно через процедуру §5.3 |
| **L3** | Вспомогательные агенты: форматирование, генерация черновиков, ревью | Только чтение. Не создают артефактов, попадающих в диплом, без проверки L1/L2 |

### 5.2. Статус SSOT-документов

| ID | Правило |
| --- | --- |
| SSOT-01 | Файлы `docs/ssot/*.md` и `docs/decisions_adr/*.md` со статусом `accepted` являются **неизменяемыми для агентов уровня L2 и ниже**. Прямое редактирование этих файлов агентом L2/L3 — нарушение процесса, изменение подлежит откату независимо от его содержательного качества |
| SSOT-02 | SSOT описывает **текущее** состояние системы, ADR — **почему** оно такое. Дублирование длинных спецификаций в ADR запрещено; ADR ссылается на SSOT |
| SSOT-03 | Изменение поведения системы без обновления SSOT — дефект процесса, а не «мелочь». Задача с таким изменением не может быть закрыта |
| SSOT-04 | При расхождении «код ↔ SSOT» **прав SSOT**. Сначала ADR + правка SSOT, затем правка кода. Обратный порядок («код уже написан, подгоним документ») запрещён |
| SSOT-05 | Каждый агент **обязан прочитать** `governance.md` и релевантные ему файлы SSOT до начала работы и явно перечислить прочитанное в своём отчёте |
| SSOT-06 | Агент L2 не вправе самостоятельно расширять Scope, даже если расширение выглядит улучшением. Предложение оформляется как запрос по §5.3 |
| SSOT-07 | Результаты работы агента, противоречащие §1.3, не принимаются целиком, без частичного зачёта |
| SSOT-08 | После Quality Gate 3 документы [`02_math_model_ssot.md`](02_math_model_ssot.md), [`01_architecture_ssot.md`](01_architecture_ssot.md), [`03_api_contracts_ssot.md`](03_api_contracts_ssot.md), [`failure_and_fallback_policy.md`](failure_and_fallback_policy.md) и имена в [`metrics.md`](metrics.md) имеют статус **LOCKED**. Правка норм `ARCH-*`, `API-*`, `FF-*`, формул (2.1)–(2.23), G-01…G-21 и имён `carbon_aware_*` агентом L2/L3 запрещена. Изменение = новый ADR (`accepted`) + правка L1, затем код |

### 5.3. Процедура запроса на изменение SSOT (SSOT Change Request)

Агент L2, обнаруживший, что SSOT неполон, противоречив или мешает выполнению задачи, **не редактирует SSOT**, а выполняет:

1. **Останавливает** работу над спорной частью задачи, продолжая бесспорную.
2. **Оформляет запрос** в отчёте `docs/audit/<task-id>-<slug>.md` в разделе `## SSOT Change Request` по форме:
   - `Затронутый документ и раздел:` — файл + идентификатор правила;
   - `Наблюдаемое противоречие:` — факты, а не мнение;
   - `Почему нельзя выполнить задачу в текущих рамках:`
   - `Предлагаемая формулировка:` — точный текст замены;
   - `Влияние на Scope:` — попадает ли предложение в §1.3;
   - `Альтернатива без изменения SSOT:` — обязательное поле.
3. **Архитектор L1** рассматривает запрос и выносит одно из решений: `accept` (правит SSOT + при необходимости ADR), `reject` (с обоснованием), `defer` (фиксирует как «дальнейшая работа»).
4. Если запрос затрагивает §1.3 (снятие запрета) — решение принимает **L0**; L1 не вправе снять запрет самостоятельно.
5. До вынесения решения агент L2 **не реализует** спорную часть.

### 5.4. Разрешение конфликтов между агентами

| ID | Тип конфликта | Правило разрешения |
| --- | --- | --- |
| CONF-01 | Два агента дают разные ответы по факту о системе | Истина — то, что записано в SSOT. Если в SSOT нет — вопрос эскалируется L1, а не решается голосованием или «у кого свежее» |
| CONF-02 | Код противоречит SSOT | Прав SSOT (SSOT-04). Код правится |
| CONF-03 | Два SSOT-документа противоречат друг другу | Приоритет: `governance.md` → ADR (`accepted`, больший номер) → [`02_math_model_ssot.md`](02_math_model_ssot.md) (нормативные формулы и предохранители; LOCKED, ADR-001) → [`01_architecture_ssot.md`](01_architecture_ssot.md) (компонентная модель; LOCKED, ADR-002 + Freeze; не переопределяет формулы) → [`failure_and_fallback_policy.md`](failure_and_fallback_policy.md) (автомат Fallback; LOCKED; не переопределяет G-* и `ARCH-*`) → [`03_api_contracts_ssot.md`](03_api_contracts_ssot.md) (REST/DTO/annotations; LOCKED; не переопределяет формулы, `ARCH-*` и `FF-*`) → `requirements.md` → `architecture.md` (указатель на `01_architecture_ssot.md`) → `interfaces.md` (указатель на `03_api_contracts_ssot.md`) → `metrics.md` (имена `carbon_aware_*`; LOCKED) → `experiment-protocol.md` → `glossary.md`. Противоречие обязательно устраняется правкой, а не «запоминается» |
| CONF-04 | ADR противоречит ADR | Действует ADR с бо́льшим номером и статусом `accepted`; предыдущий помечается `superseded` |
| CONF-05 | SSOT противоречит инженерной спецификации | `engineering-specification.md` — входной канон, но не переписывается. Расхождение фиксируется ADR с явным указанием, что и почему уточнено |
| CONF-06 | Спор о трактовке границ Scope | Действует SCOPE-EDGE-01: неоднозначность трактуется в пользу Out-of-Scope |
| CONF-07 | Спор о технической реализации внутри принятых рамок | Решает L1; критерии выбора — воспроизводимость, простота, соответствие Kubernetes-практикам, влияние на защищаемость результата, именно в этом порядке |
| CONF-08 | Спор об экспериментальном результате | Решается повторным прогоном по §6, а не обсуждением. Побеждает воспроизводимый результат |
| CONF-09 | Агент утверждает, что задача выполнена, но чеклист DoD не заполнен | Задача считается невыполненной |
| CONF-10 | Конфликт слияния в git | Разрешает автор более поздней ветки; при затрагивании SSOT — только L1 |

### 5.5. Обязательный протокол работы агента

Каждый агент пайплайна выполняет строго следующую последовательность:

1. Прочитать `docs/ssot/governance.md` (этот документ) и релевантные SSOT-файлы.
2. Проверить задачу на соответствие §1.3 (Out-of-Scope). При попадании — остановиться и сообщить, а не «сделать поменьше».
3. Выполнить задачу в границах Scope.
4. Проверить результат по применимым чеклистам §2.
5. Обновить затронутые SSOT-файлы **только если уровень доступа это позволяет**; иначе — оформить SSOT Change Request (§5.3).
6. Записать отчёт в `docs/audit/<task-id>-<slug>.md`: что сделано, чем подтверждено, заполненный чеклист DoD, открытые вопросы, следующий шаг.
7. Передать контекст следующему агенту явным перечнем: какие файлы созданы/изменены, какие решения зафиксированы, какие вопросы остались открытыми.

## 6. Требования к воспроизводимости экспериментов

Принцип: **любой результат, попадающий в диплом, должен воспроизводиться третьим лицом по содержимому репозитория без обращения к автору.**

### 6.1. Детерминированность входных данных

| ID | Требование |
| --- | --- |
| REPRO-01 | Эксперименты выполняются только в **replay mode** на зафиксированном историческом датасете углеродной интенсивности. Live API запрещён (SCOPE-EDGE-06) |
| REPRO-02 | Датасет хранится в `experiments/datasets/` (или вне git с зафиксированным sha256 и инструкцией получения), имеет версию (VER-20) и не редактируется после первого использования в опубликованном прогоне |
| REPRO-03 | Replay Engine воспроизводит временной ряд по модельному времени сценария, а не по wall-clock; стартовая точка ряда задаётся в карточке эксперимента |
| REPRO-04 | Все псевдослучайные генераторы (генератор нагрузки, порядок submit, jitter) инициализируются явным seed из карточки сценария |
| REPRO-05 | Нагрузки описаны декларативно в `experiments/workloads/`; интерактивное создание Pod вручную запрещено |
| REPRO-06 | Параметры модели (\(P_{idle}\), \(P_{max}\), веса \(w_C,w_R,w_P\), `maxDataAgeSeconds`, SLA) задаются в конфигурации сценария, а не в коде |

### 6.2. Идентификация прогона

| ID | Требование |
| --- | --- |
| REPRO-07 | Каждый прогон имеет `run_id` формата `<scenario-id>_<strategy>_<YYYYMMDD-HHMMSS>_r<N>`, где `strategy ∈ {default, carbon-only, proposed}`, `N` — номер повтора |
| REPRO-08 | Все артефакты прогона складываются в `experiments/results/<run_id>/`: сырые метрики, лог решений планировщика, manifest окружения, копия конфигурации сценария |
| REPRO-09 | `run_id` указывается рядом с каждым числом и графиком в тексте диплома (DOD-DOC-10) |

### 6.3. Manifest окружения (обязателен для каждого прогона)

Файл `experiments/results/<run_id>/environment.yaml` фиксирует минимум:

- commit SHA репозитория и наличие незакоммиченных изменений (прогон с «грязным» рабочим деревом недействителен);
- версии: Go, Kubernetes (точная patch-версия), kind + digest node-образа, Prometheus, Grafana, Python + содержимое `requirements.txt`;
- топология кластера: число узлов, распределение по зонам, ресурсные лимиты узлов;
- параметры энергомодели и весов;
- идентификатор и sha256 датасета CI;
- значения seed;
- хост-окружение: ОС, CPU-модель, число ядер, объём RAM;
- дата и время прогона.

### 6.4. Статистическая корректность

| ID | Требование |
| --- | --- |
| REPRO-10 | N ≥ 5 повторов на конфигурацию; для итоговых выводов диплома по ключевым сценариям — N ≥ 10 |
| REPRO-11 | Публикуются N, mean, median, p95, разброс. «Снижение на X %» без разброса и N — недопустимая формулировка |
| REPRO-12 | Сравнение стратегий выполняется на **идентичных** датасете, нагрузке, топологии и seed. Различие допускается только в исследуемом факторе |
| REPRO-13 | Критерий исключения прогона (например, сбой инфраструктуры) формулируется в карточке **до** прогонов и применяется механически; исключённые прогоны перечисляются в отчёте |
| REPRO-14 | Warm-up прогон не учитывается в статистике и помечается как таковой в карточке |
| REPRO-15 | Sensitivity analysis обязателен там, где вывод зависит от некалиброванного параметра (в первую очередь \(P_{idle}\), \(P_{max}\)) |

### 6.5. Воспроизведение и аудит

| ID | Требование |
| --- | --- |
| REPRO-16 | Полный цикл «поднять стенд → прогнать сценарий → получить графики» выполняется командами из репозитория (`make kind-up`, скрипт сценария, скрипт анализа). Недокументированных ручных шагов быть не должно |
| REPRO-17 | Скрипт анализа детерминирован: повторный запуск на тех же сырых данных даёт идентичные числа и графики |
| REPRO-18 | Ограничения и допущения эксперимента перечисляются в отчёте о прогоне явно (оценочный характер энергии, модельные энергозоны, отсутствие сетевого и embodied carbon) |
| REPRO-19 | Отрицательные и противоречащие ожиданию результаты сохраняются и публикуются наравне с остальными |
| REPRO-20 | Демонстрация на защите (live mode) отделена от экспериментальной части и никогда не используется как источник чисел |
